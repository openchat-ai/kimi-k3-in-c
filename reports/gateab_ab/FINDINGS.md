## 一、为什么这份定稿这么短

因为今天（及此前两天）做的 19 次端到端 `s/词元` 测量，**没有一次能支撑所宣称的效应量**。

```
同一份源码、同一脚本、连续三轮：65.21 / 75.62 / 79.91 s/词元     跨度 22.5%
19 次 3 词元无预取运行：min 65.21   median 79.23   max 89.88      跨度 31%（中位的）
```

被拿来对比的配置差异，全部是 1–7% 量级：

| 结论 | 声称效应 | 相对噪声 |
| --- | --- | --- |
| prefetch 变慢 | 0.75× / 0.60× | 部分可分辨，但仅 2 个点 |
| 异步突发变慢 | +12 s/词元 | 不可分辨 |
| 跨层流水 8.4% | −8 s/词元 | 不可分辨 |
| 四个提交的"单调退化" | 每步 1–4% | 完全不可分辨 |

**结论反复翻转不是系统难懂，是实验功效不足。** 一个 22–31% 噪声的负载，
被用来判定 1–7% 的差异，每加入一个新数据点就翻一次结论，是必然的。

规程里写的"真实离散 11.6%"只描述 v30+v34 那六轮，**不描述这个工作负载**。
把它外推成基线纪律是错的，已撤回。

## 三、这些数字对你意味着什么

### 3.1 参数调优这条路**没有**走完（2026-10-05 修正）

```
引擎专家流实际取得    345 – 460 MB/s 聚合
设备同一形态实测      1471 / 1560 / 1519 MB/s   （v60，三对，同字节量、固定读取次数）
                      与 v55 独立测得的 4M 顺序 1537–1626 吻合
→ 余量 3 – 4 倍，不是零
```

**本节此前据"设备该形态约 368 MB/s"写下的"旋钮已耗尽、不要再扫参数"予以撤回。**
那个 368 是一次探测的产物（见第二节 C 类）。**设备在该形态上能跑约 1500，
引擎拿到 400 上下，中间的 3–4 倍没有被解释，也尚未被取用。**

**因此 prefetch 深度、arena 大小、内存配比、worker 数量这四类旋钮
不应被排除，只是今天试过的那些组的效应量落在噪声内 —— 这与"旋钮无效"是两件事。**

**取用这 3–4 倍的入口是 3.4 那个问题：设备有能力，而 worker 有 40–49% 的时间
不在发请求。注意"并发只有 9"与这 40–49% 是同一测量的两种说法，不构成两个独立缺口 ——
详见 3.4 的更正。**

### 3.2 差距是结构性的，不是 bug

```
一条层读完 → 算 → 才读下一层
worker 有 40–49% 在睡觉，队列只积压 3%
```

**盘不是被浪费，是"没有请求可发"。** 这解释了为什么 13 次外部实验都找不到
"哪里慢" —— **没有可优化的地方，只有等待下一个请求的固有空隙。**

### 3.3 要更快，只剩三条路

```
① 换设备          不同形态的盘，或多盘并行        ← 采购决策，不在代码内
② 取用那 3–4 倍   设备该形态约 1500，引擎拿到 345–460   ← 见 3.4，唯一在代码内有量级的方向
③ 少读            量化 / 缓存复用                ← 正是本文的主题
```

**② 的量级已由 v60 确定**（此前以为不存在），**它的入口是 3.4 那个并发问题**，
而不是继续扫参数。

### 3.4 那 3046 次 `cond_wait` 的延迟来源，是唯一还开放的问题

**先更正一个此前被当成独立发现的现象。** 本节曾把"并发只有 9"列为开放问题，
并把设备—引擎的 3–4 倍差距挂在它下面。**这两件事是同一个测量：**

```
16 worker ×（1 − 睡眠占比）= 有效并发
16 × 0.60 = 9.6     16 × 0.555 = 8.88     16 × 0.51 = 8.16
实测并发 8.9 – 10.0×      ✓ 落在该区间内
```

**"并发只有 9"没有独立于"睡眠 40–49%"的额外信息**，把它当第二个证据会重复计数。
原先 3.1 与 3.4 两处并列陈述，已合并。

**而 8.9–10.0 与本机物理核数相符：** Hygon C86-3G，8 物理核 / 16 逻辑处理器
（WSL 侧 `nproc`=16，`lscpu` 报 16 socket × 1 thread/core，是 WSL 的合成拓扑，不可用）。
8 核 × 1.1–1.25 倍 SMT 增益 = 8.8–10.0，与实测区间重合。

**据此，"加 worker"这条路的天花板约在 8–10，与实测一致 —— 不是没有头寸，是头寸就在核数上。**

```
sleep 40 – 49%（3046 次 cond_wait）
queue 3.1 – 4.2%
```

**真正未解释的是这两行的组合**：worker 有四成时间在睡觉，而队列几乎不积压。
"请求到达得太晚"（producer 供不上）与"worker 被 CPU 调度走"
在队列深度上无法区分 —— 后者手上的请求已出队、处于 in-flight，队列深度看不到它。
**本节此前用队列仅积压 3% 排除 CPU 饥饿，那个推理不成立。
判定已于 2026-10-07 完成，结论在 3.5：非 CPU 受限。**

### 3.5 判定结果（v64，2026-10-07）：非 CPU 受限，成因是层间流水结构

以 `/proc/<tid>/schedstat` 直接测得。**该字段是内核记账而非硬件 PMU 计数器，
故本平台无 `cpu` perf / `uncore_imc_*` / MSR 这条限制不影响此判据**；
起止各留快照、中间每 2 s 覆盖一次最后一次，**不需重编译引擎**，
26 个 proc 小文件 13 次读/秒对以分钟计的运行扰动可忽略。

```
线程                       在核        运行队列等待   等待/在核
主线程（producer）          92.15 s      2.59 s      0.028
16 个 kio worker        各 48–58 s  各 1.9–3.3 s    0.039–0.063
另 4 个线程            各 23.2–23.5 s  约 2.5 s      0.105–0.111
──────────────────────────────────────────────────────────────
合计（21/26 线程）        1007.4 s     52.7 s        0.052
```

**判定为非 CPU 受限**，三条独立依据：

1. 饱和时运行队列等待应 ≳ 在核时间（比值 ≳ 1），实测全部 ≤ 0.111；
2. 在核总量 1007.4 s ÷ 墙钟 314 s = **3.2 核 / 8 核 = 40% 占用**；
3. 队列等待 52.7 s 占可用核时（314 × 8 s）的 **2.1%**。

且 worker 在核仅占墙钟 16%，说明它们**真正阻塞在 `cond_wait` 而非自旋**
（若为忙等，在核时间会接近墙钟）。

**结论：那 40–49% 是等下一个请求迟到。处置是改生产者节律
（在算术期间发出下一层的读），不是加 worker，也不是改等待方式。**

**运行 `reports/gateab_ab/probe_schedstat.sh`；原始件 `reports/gateab_ab/v64_schedstat/`。**

> **预设判定带的一处失误。** 脚本里预置的规则把比值 0.02–0.20 定为"两者兼有"，
> 实测 0.052 落入该带，脚本因此输出"介于两者之间"。**该带没有与物理参照挂钩**——
> 饱和意味着比值 ≥ 1，0.052 明显偏于不受限一侧；而绝对占用（40%）才是决定量。
> **原始输出与预设带都保留未改**（`v64_schedstat/`、`v64_probe_attempt1.out`），
> 判定按绝对量重做。这是"先定规则再测数"的一次教训：阈值必须绑定物理参照，
> 否则"中间地带"会把自己的结论吞掉。

**附带结论（字节 vs 时间）**：v64 的字节量与本文件第三节逐项相同
（4595 reqs、216.66 GB、group0 235/140.16 GB、group1 4360/76.51 GB、
并发 9.0×、sleep 49%、queue 2.7%），但墙钟 104.66 s/词元 高于已记录的 65.21–89.88，
专家流每流速率降到 29 MB/s（记录区间 34–46）。**字节恒定而速率漂移，
已记录的时间上界因此上推至 104.66 s/词元。**

**这条不需要跑 `s/词元`**：`stat_sleep_ns` 与 `stat_sleep_n` 已可信，
直接读等待次数与唤醒延迟分布即可。

### 3.5 不要再用 s/词元 做任何判定

```
同配置同源码连续三轮 65.21 / 75.62 / 79.91   跨度 22.5%
19 次合并             65.21 – 89.88            跨度 31%（中位的）
```

规程里的判据：

```
配对交错 ≥5 轮，且效应 ≥10%     才可判定"有差异"
效应 <10%                       一律写"无差异"，不再重跑
n=1 或 n=2 的单次对比           一律不作为结论
```

**这一条比本文件任何一个数字都值钱。** 它能省掉后续所有这类返工。

## 六、方法论：这一轮的教训

四个仪器缺陷，全属"探针的失败模式与真实故障长度一致，而探针不自检"：

1. 短读被解释为"越界"，而 `errno` 说的是 `EBADF`
2. `NSLOT` 自己算（300 GB ÷ slot）而不读引擎打印的真值
3. 传给 `pthread_create` 的结构体声明在循环体内，靠栈内存侥幸存活
4. 报告挂在 `k3_io_free` 上，而引擎从不调用它（退出时 worker 仍在跑）

以及三条本轮新增：

5. 求和 `dd` 每次调用的速率 —— 在 v55 正确（全部并发），在 v57 错误（每流是串行链，
   放大 120 倍，打印出 12411 MB/s 的物理不可能值）
6. 烟测把块大小写成字面 `4194304`，而脚本用变量 `"4M"`，于是烟测跑的是
   **另一条代码路径**，`$((per/bs))` 报"value too great for base"，11 组全灭
7. 十二个 `dd` 追加到同一个文件导致行截断，且脚本已删除原始输出，证据丢失

**规程 `BENCH_PROTO` 第 13.5 条由此而来：烟测必须调用被测函数本身，
不得复制其逻辑或改写其参数；长跑内自检失败必须中止，且必须保留证据。**

**另一条更贵的教训：一个 22–31% 噪声的负载，不存在能判定 1–7% 差异的实验设计。**
无论用多少轮、怎么配对、怎么统计，这个功效缺口都在。**唯一的解法是换判据**——
用 `per-stream MB/s`、`queue_s`、`sleep`、duty cycle 这些在多轮下不动的量，
而不是端到端时间。

## 七、唯一还开放的问题

**见 §3.4**，此处只留原始出处与未证实项：

```
sleep 40 – 49%（3046 次 cond_wait），queue 3.1 – 4.2%
```

worker 有四成时间在睡觉，而队列几乎不积压——**不是没有请求排队，
是请求到达得太晚。** 这与每词元 7.34 s 的关键路径算术有关联，
**但该关联未证实**（7.34 s 本身来自 `overlap_sim.py` 的 ab56 口径，未独立复核）。

v60 之后，这个缺口的分量由"结构性、无收益"变为**承载设备侧 3–4 倍余量**（§3.1、§3.4）。

**这个问题不需要跑 `s/词元`**：`stat_sleep_ns` 与 `stat_sleep_n` 现在是可信的，
直接看等待次数与唤醒延迟分布即可。
