## 1 平台与运行环境

| 项 | 值 |
| --- | --- |
| CPU | Hygon C86-3G，**8 物理核 / 16 逻辑处理器**（WSL 侧 `nproc`=16；`lscpu` 报 16 socket × 1 thread/core，系 WSL 合成拓扑，不可采信） |
| 内存 | 56 GB |
| 源盘 | 机械盘，近满，挂载于 `/model`（只读，模型权重） |
| 数据盘 | SINKER SEV512THK-CEN NVMe，1 盘 384 GB，ext4 |
| 主机环境 | Windows + WSL2，磁盘分区直挂为块设备（非 VHDX 镜像） |
| 客体内核 | Linux 5.x，x86_64，gcc |
| 构建 | `make -j8`，`-O3 -march=native -fopenmp -pthread` |
| 推理引擎 | 本项目自研纯 C 引擎 `bin/k3` |

**关键环境限制（复现者须知）**

1. **WSL2 后台会话不继承已挂载磁盘。** 通过任务计划程序或后台进程启动的 WSL 会话中
   `/mnt/nvme` 为空目录，必须在该会话内自行挂载，否则引擎报
   `cannot open .../embed/...` 而失败。本项目的运行脚本已内置该挂载步骤。
2. **WSL2 不强制 memory cgroup 限制。** `systemd-run -p MemoryMax=512M` 下真实分配并写入
   1024 MB 的测试进程仍成功（`reports/gateab_ab/test_memcap2.sh`，脚本自身输出亦为
   "分配并写入 1024 MB"，即 `bytearray(1024*1024*1024)`）。
   **故正文原表 3 所依赖的 26 GB 硬内存上限在本平台不可施加**，该表已删除（见第 6 节）。
3. **本平台无硬件 PMU**：无 `cpu` perf 事件源、无 `uncore_imc_*`、无 `/dev/cpu/0/msr`。
   可用观测面为 `/proc/diskstats`、`/proc/vmstat`、宿主 `Get-Counter \PhysicalDisk(*)`、
   引擎自报计数器。**本说明中的一切数据均不依赖硬件计数器。**
4. **8 物理核决定了 worker 数的天花板，配置时须以此为准。** 实测 16 个 worker 的有效
   并发为 8.9–10.1×，而 `16 ×（1 − 睡眠占比 40–49%）= 8.2–9.6`，二者一致 ——
   有效并发就是 worker 数乘以它的工作占比，**不构成独立的第二个缺口**。
   8–10 的实测值与 8 物理核 × 1.1–1.25 倍 SMT 增益重合，故 worker 数超过 8–10 不再
   增加并行度。
5. **无 PMU 不妨碍判定线程是否被 CPU 饿着：用 `/proc/<tid>/schedstat`，它是内核记账
   而非硬件计数器。** 字段依次为在核纳秒、在运行队列上等待的纳秒、时间片数。
   **判据**：饱和时运行队列等待应 ≳ 在核时间（比值 ≳ 1）。
   2026-10-07 实测（`reports/gateab_ab/probe_schedstat.sh`，21/26 线程）：
   主线程 92.15 s 在核 / 2.59 s 等待（0.028）、16 个 worker 各 48–58 s 在核、
   比值 0.039–0.063、合计在核 1007.4 s ÷ 墙钟 314 s = **8 核中的 3.2 核（40%）**，
   队列等待仅占可用核时 2.1%。**结论：非 CPU 受限**，那 40–49% 是等下一个请求迟到，
   处置为改生产者节律，而非加 worker。
   **取样方式**：起止各留快照，中间每 2 s 覆盖一次最后一次（`schedstat` 是单调累计量，
   必须在进程退出前取；退出后 `/proc/<pid>/task` 已消失）。
   **不需要重编译引擎**，也不需要修改被测代码。
6. **空闲门禁的两个已确认漏洞（2026-10-07 补）。** 现有门禁只看 `loadavg(1min) < 0.5`
   且只在起点采一次样，据此**已知一次运行被污染而门禁通过**：
   - **漏洞一：门禁不识别系统维护活动。** v65（`reports/gateab_ab/v65_hitwall/`）运行窗口
     09:26:18–09:42:26，而 `unattended-upgrades` 于 09:26:53 启动、09:28:15 列出 60 余个待升级包
     （含 libc6、coreutils、perl、python3.14）、09:35:11 装完（`/var/log/dpkg.log`）。
     apt 的工作目录是根文件系统而非 `/mnt/nvme`，loadavg 因而在门禁采样时刻可能低于 0.5。
     **该次运行的字节量仍为 4595 reqs / 216.66 GB，但速率不可用，故判 `CANNOT MEASURE`，
     原始件保留不删。**
   - **漏洞二：门禁只测起点，不测全程。** loadavg 会在运行中途起伏。
   **故新增两条门禁**：①`pgrep 'apt|dpkg|unattended-upgr'` 非空即中止；
   ②运行期间每 30 s 复检 loadavg，任一次超标即作废该轮。

## 3 测量纪律（复现者必读）

**本项目的性能类观测量的可重复性远低于直觉，直接影响哪些数字可复现。**

### 3.1 稳定与不稳定

```
字节类观测量（每词元请求数、字节数、每流速率、队列时长）   10 轮逐位一致
s/词元（端到端速度）                              同源码连续三轮跨度 22.5%
```

三例（同源码、同配置、连续三轮）：

```
2026-09-30   65.21  75.62  79.91 s/词元      跨度 22.5%
2026-09-29   76.04  73.39  74.91             跨度  3.6%
v59 二分首点  83.60（与前二者同源码）
```

**结论：不得引用跨时段的绝对速度作对比。**

### 3.2 判定门槛

凡以速度为观测量作配置间对比，须同时满足：

- 同一时段内交错配对重复 ≥ 5 轮
- 配对差 ≥ 10%
- **配对差自身的离散显著小于该效应**（若配对差翻符号，或离散达到其中位，
  判定为 `CANNOT MEASURE`，即本次测量作废）

**`CANNOT MEASURE` 与"无差异"后果相反**：前者是"什么都不能决定"，
后者是"效应已确认小于门槛，可按其他依据决定"。**不得混同。**

完整规程见 `reports/gateab_ab/BENCH_PROTO.md` 第 13、14 节。

### 3.3 探针自检

新探针在长跑前必须短烟测并自检：文件几何取自引擎或文件本身（不猜）、
时钟分辨率已验、短读打印 `errno/offset/length`、stride 与槽数互质、
传给 `pthread_create` 的结构体活过所有线程。**烟测必须调用被测函数本身，
不得复制其逻辑或改写其参数。**

## 6 已知不可复现的部分（如实声明）

**原表 3（L1 替换策略对照）已从稿件删除。** 三条理由：

1. **无源。** 其六个数值（107.27 / 96.35 / 106.52 / 100.17 / 20.99 / 17.44）
   在字节级台账中出现 **0 次**；稿件原表 A.1 将其指向的台账行号
   （`:17, :21, :58-:67`）实为"字节流分类总纲"与 BF8 压缩估算，与策略对照无关。
2. **前提不可施加。** 该对照限定 cgroup 26 GB 硬内存上限，本平台为 WSL2，
   不强制 memory cgroup（见第 1 节第 2 点），该前提无法实现，
   故既不能复现也不能否证。
3. **无上限条件下效应不存在。** 以 {LRU, heat} × {8, 15} GB 四臂各 3 轮复现，
   专家段字节**逐轮一致**（LRU 25.83、heat 25.50 GB/词元），
   即 heat 相对 LRU 仅 **−1.3%**，且 cache 由 8 GB 增至 15 GB 字节完全不变，
   与原表所载 −19% / −32% 不符。因字节列三轮零离散，效应若有 19% 必会显现。

**该节曾支撑的"替换策略是独立于介质落位之外的第二个影响因素"一说随之撤回，
不在稿件摘要与结论中出现。** 稿件 4.5 节保留了完整删除说明，未隐去。

**另有两项如实声明：**

- **速度类观测量的可重复性不足**（3.1 节）。故稿件 4.6 节**不给出**剩余性能差距的
  可达上限，只陈述该差距"非字节所致、亦非设备能力不足"。
- **部分早期探针数据不可用**：曾出现短读被解释为"越界"（`errno` 实为 `EBADF`）、
  槽位数自行推算、探针输出文件竞争导致半数读取静默失败等情况。
  相关结论已撤回，过程记录保留在 `reports/gateab_ab/DAY1/summary.txt`
  与 `FINDINGS.md` 的撤回清单中。

### A.2 对照收益与乐观上界的差距

- **字节量推演上限**：每词元 25.83 GB 中约 90% 来自跨遍复用（台账 :349）；若能在高速内存（DRAM）层完整复用，字节量可降至约 10%（“约 −90%”）。该推演以“跨遍路由单调超集、路由稳定”为前提。
- **真机命中实测**：gen=32 长程累计高速盘命中为 74.89%（含冷启动 miss，台账 :356, :412）。这与阶段 B 所述的“CACHE HIT 100%”不矛盾——后者是稳态时每步（STEP 表）观察（词元≥5 后专家键全命中，台账 :348），前者是含冷启动的全程累计口径。
- **差距来源**：−37% 未及 −90%，因为复用仍落在高速盘（sdd7）而非高速内存（DRAM）层——每词元仍搬 25.83 GB，白板命中同样不能免除字节搬运，瓶颈转移到介质带宽。

### A.3 观测口径

READ 计数为引擎内建字节级计数，按 pread 实际请求字节数累计；实测值（25.83 GB）与理论载入（层数 × 激活专家数 × 单专家字节）逐字节吻合，说明计数并不包含“额外读取”。台账如实记录进程挂死/FAIL 条目（波形如低速盘巨型 O_DIRECT pread 的 D-state 永久挂起），未选择性剔除负样本。

输出速度以引擎报告的 `seconds_per_token` 为准（每词元端到端墙钟时间），表 1 的专家段耗时由 READ 字节数与引擎内部分段计时交叉验证。正文所引速度数字均为一次运行的实测记录；因运行间存在波动（见台账关于 run-to-run 区间的记录），关键读数以 n=3 重复的中位数报告（§4.5），其余单次读数标注出处。
